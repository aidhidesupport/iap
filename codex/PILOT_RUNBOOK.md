# 一組・一案件でIAPを試す

2026-09-22 / partial-standardsの提案を、試行から改善するための手順

目的は、提出前にずれを見つけて修正できるか、短い共有で相手に状況が伝わるか、双方の負担が増えすぎないかを確かめることです。実案件の試行は未実施です。

## 開始前

別々のPM・開発者と、30〜60分で途中成果を確認できる案件を選びます。目的・完成条件・対象外・読む成果・共有先・時間上限を一枚にします。架空化できる入力を使い、記録の保存先・期間・削除担当と、公表してよい範囲を決めます。

Codex連携を使う場合は [開発者ガイド](https://github.com/aidhidesupport/iap/blob/main/CODEX_GUIDE.md) で案件への配置とフックの有効化を確認します。PMは [依頼・確認のガイド](PM_GUIDE.md) を読み、既存のチャットを使います。Web先行試作への二重入力は求めません。

## 進め方

1. PMが依頼を伝え、開発者とCodexが条件を記録する。
2. 開発者側で作業・照合・範囲内の修正・テスト・再確認を進める。
3. 進捗・残り・次の一手・確認事項を共有する。判断事項がなければ、毎回の返答待ちにしない。
4. 条件変更が必要な場合はPMへ判断を求め、回答と対象の版を記録する。
5. PMが成果を確認する。Codexの評価を人による受け入れに置き換えない。
6. 双方が負担と使いにくかった点を短く記録する。必要なら途中で中止し、再開の一手を残す。

## 測るもの

| 観点 | 記録 |
|---|---|
| ずれと修正 | 発見時点、根拠、修正内容、未完成と逸脱の区別、誤警告 |
| 人の負担 | 開発者・PM・支援者それぞれの確認・調整時間 |
| 手戻り | 誤解による作業と、通常の実装・探索を区別 |
| 共有 | 要約生成、文章の手直し、送信操作、PMの確認を分ける |
| 判断待ち | 判断依頼から回答までの経過時間。人の実作業とは別 |
| 次も使うか | PMと開発者に別々に聞き、理由を残す |

要約の再観測・生成時間はコマンドで記録できます。人の時間や回答は本人の実測・申告によります。未回答は不明、実際に不要だった場合だけ根拠付きの0です。内数になっている指標を重複加算せず、比較案件がなければ時間削減率を出しません。

## 試行後

成立した手順、詰まった箇所、余計な負担、必要だった共有を整理します。困った箇所を小さな反証例にし、仕様やガイドを修正します。追加機能はその結果から選びます。

初回の目的は購入判断の確認ではなく、提案を確かめることです。使いにくかった結果も残し、協力者への連絡・記録の公開はそれぞれ具体的な合意の範囲で行います。
